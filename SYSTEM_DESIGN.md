# System Design — CuraVia Health (690w)

## 1. Double-Booking Prevention
**Threat:** two patients view same slot and confirm simultaneously.
**Decision:** compute availability on-the-fly from doctor_profiles.workingHours minus appointments(HELD/CONFIRMED) and doctor_leaves, not pre-generated rows. generateSlots walks start?end stepping slotDurationMinutes. **Booking:** GET /doctors/:id/availability excludes active HELD/CONFIRMED where holdExpiresAt>now and leave dates. POST /appointments/hold creates HELD with holdExpiresAt+10m inside transaction that checks (doctorId,slotStart) active conflicts; UNIQUE(doctorId,slotStart) is hard guard — second racing INSERT gets P2002 ? 409. Uses $transaction SELECT equivalent. **Confirm:** HELD?CONFIRMED if not expired else 410. LLM/email after commit never blocking. **Proof:** tests/concurrent-booking.js two parallel holds ? 1×201 1×409. **Indexes:** appointments(doctorId,slotStart) unique + status, patientId ensure hot-path index scans, constraint is concurrency semaphore.

## 2. Leave Conflict Handling
**Requirement:** marking leave (single/range) must free calendar and notify. **Flow POST /doctor-leaves:** creates doctor_leaves, queries appointments WHERE doctorId=X AND status IN (HELD,CONFIRMED) AND slotStart BETWEEN start/end, each set to CANCELLED, enqueues LEAVE_CANCELLATION email, deletes calendar event best-effort, writes audit_log. Notifications async; leave never fails due to email. Future availability for range returns []. **Proof:** leave-cancellation.js books day+2, posts leave ? cancelledCount 1, status CANCELLED, notification_log LEAVE_CANCELLATION exists. **Edge:** leave overlap allowed, delete does not resurrect cancelled — patient must rebook (avoids double-notify).

## 3. Hold Mechanism & Expiry
**Why holds:** symptom form takes time; without holds two users proceed to confirm and one gets late error. Holds give 10m exclusive window. **Lifecycle:** Held = status HELD holdExpiresAt now+10m. Visibility: availability excludes HELD where holdExpiresAt>now; expired considered free. Confirm if now<holdExpiresAt ? HELD?CONFIRMED + symptom_forms with LLM; else 410 and frontend refresh. Expiry: jobs/worker.ts * * * * * every minute updateMany HELD&&holdExpiresAt<now ? CANCELLED (mock iterates). Logs via Pino. Guarantees abandoned holds don't block slot. Retry: expired just-before-confirm rejected 410 prompting slot refresh. TTL balances UX (fill symptoms) vs throughput.

## 4. Notification Failure Handling & Retry
**Invariants:** booking/leave/visit never rolled back because email failed. Calendar best-effort. All logged. **Architecture notifications.ts:** enqueueNotification writes notification_logs PENDING, pushes queue, processQueue async builds HTML via templatedEmail, calls sendEmail; on fail and retryCount<3 re-queues with backoff 2^retry*1000ms (1s/2s/4s) else FAILED. Cron also retries PENDING/FAILED where retryCount<3. All logs via Pino; admin dashboard shows logs and llmStatus, stats pending/failed. **SMTP pluggable:** empty SMTP_HOST ? jsonTransport stub; prod swaps via env. **Guarantees:** booking returns 201 even if sendEmail throws; caller sees success and notification PENDING?SENT/FAILED. Admin sees notificationsFailed in /admin/stats. **Calendar:** same best-effort (services/calendar.ts — if GOOGLE_CLIENT_ID empty, stub logs + mock calendar_events SYNCED; failures log FAILED not auto-retried but could be queued similarly). LLM likewise never blocks booking (services/llm.ts fallback with timeout 10s, retry once, fallback).
